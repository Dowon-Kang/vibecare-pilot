# 인수 분석 요약

## 프로젝트 정의

[사실] **VibeCare Pilot은 고령 연구 참여자의 체성분 측정 4건과 안전 응답을 바탕으로 연구용 진동 설정을 계산하고 Mock 전송·실행·중지 흐름을 시험하는 프로토타입이다.** 근거: `README.md`, `design.md`, `mobile-app/lib/controllers/pilot_controller.dart`, `backend-api/src/index.ts`.

## 실제 완성도

[사실] Mock 앱은 작동하며 기존 테스트 23개(웹 5·Worker 8·Flutter 10)가 이번 분석에서 통과했다. 웹 빌드, 웹/Worker TypeScript 검사, Dart 정적 분석도 통과했다. 전체 oxlint는 기존 오류 2개로 실패했다. 기존 웹 서버에 HTTP 200을 확인했다.

[사실] 운영 연동 제품은 **미완성**이다. FITRUS 프록시는 원본 응답만 보존하고 `normalized:false`를 반환한다. 추천용 BIA·vitals 저장 경로, 참여자 발급 절차, 실제 진동기 어댑터, 앱 피드백·자동 토큰 갱신이 없다. Worker D1 ID는 placeholder이며 release 서명은 debug 키다. 코드량이나 체크박스로 완성률을 숫자로 환산할 근거가 없다.

[사실] “테스트 통과”와 “안전 요구 충족”은 일치하지 않는다. Flutter 기본 로그인 후 문진 없이 전송·시작하는 동작이 현재 위젯 테스트에 포함되어 있다. `design.md`의 명시적 문진 규약과 충돌한다.

## 현재 동작

1. Flutter는 `VIBECARE_API_BASE_URL`이 없으면 Mock 인증·측정·장치를 선택한다.
2. 로그인 후 최근 유효 4건을 선택하고 평균 및 파일럿 계수를 계산한다.
3. 사용자는 자동 추천 이하로 강도를 낮출 수 있다.
4. “장치로 보내기”는 Mock 허가 또는 Worker 허가를 받는 단계다. 실제 기기 전송은 아니다.
5. 시작하면 Mock 상태와 타이머를 갱신한다. Worker 모드는 DB 세션과 가짜 ACK를 기록한다.
6. 중지·완료·백그라운드 이동 시 중지를 요청한다. 네트워크 중지 실패에 대한 복구는 부족하다.

웹 비교 화면은 별도다. 로그인·Worker 연동 없이 고정 데이터로 추천·명령 JSON 미리보기를 만든다.

## 핵심 구조

[사실] Flutter(Material 3) → Riverpod `PilotController` → Repository/DeviceGateway → Hono Worker → D1 구조다. 추천 엔진은 Dart·Worker TypeScript·웹 TypeScript에 중복 구현되어 있다. FITRUS는 Worker의 `x-api-key` POST 경계 뒤에 있고 물리 장비 어댑터는 없다. 학습 모델·LLM·프롬프트는 없다.

## 우선 해결할 문제

| ID | 심각도 | 확인 내용 |
|---|---|---|
| I-01 | Critical | 같은 Idempotency-Key를 알고 있으면 다른 참여자의 세션·명령을 돌려받음. 실제 Hono+SQLite 격리 재현 200 |
| I-02 | High | Flutter 문진 미응답이 false로 처리되어 문진 없이 시작 가능 |
| I-03 | High | 서버가 체지방량/체중·BMI/키 일관성을 검사하지 않음. 불일치 입력에도 READY 재현 |
| I-04 | High | 모든 규칙을 비활성화해도 활성 기본 규칙으로 fallback, 실행 허가 201 재현 |
| I-05 | High | 중지 실패 시 장치 상태가 error가 되어 중지 버튼이 사라지고 앱 타이머도 취소됨(정적 경로 확인) |
| I-06 | High | 별도 허가 두 개로 같은 기기에 RUNNING 세션 두 개 생성 가능(격리 재현) |

추가 문제: 최근 불량 20건이 이전 유효 4건을 가림, 기기 ID 의미 혼용, 프로필 편집값 미저장, JSON Schema와 응답 불일치, 완료 이벤트가 상태를 변경하지 않음, 자동 갱신 부재, 과도한 Mock/API 완료 표현. 전체 근거·영향·재현·해결안은 [08_VERIFICATION.md](08_VERIFICATION.md)에 있다. 위 위험이 실물 출력 사고로 재현됐다는 뜻은 아니다. 현재 실제 출력 경로는 차단돼 있다.

## 중요 확인 사항과 질문

1. 이번 납품 완료 범위는 Mock 데모인가, 서버 연결 파일럿인가, 실기기 운용인가?
2. BIA 측정 기기와 진동 기기는 무엇이며 각각 어떤 ID와 소유 관계를 갖는가?
3. FITRUS의 성공 요청·응답·단위·품질·오류 계약을 제공받을 수 있는가?
4. 미응답 문진 차단, 규칙 승인·전체 중단 권한을 누가 책임지는가?
5. 실제 장비의 ACK·정지·통신 단절·진폭·가속도 기준은 무엇인가?

## 가장 먼저 할 작업 5개

1. 세션 멱등 조회를 참여자·요청 내용과 결합하고 교차 참여자 회귀 테스트 추가.
2. Flutter 문진을 미확인/예/아니요로 분리하고 미확인 실행 차단.
3. 세 엔진의 입력 검증·규칙 비활성 동작·공통 fixture 검사 일치.
4. 중지 실패 복구와 기기별 실행 잠금·완료 상태를 하나의 세션 규약으로 정의.
5. FITRUS·기기 계약과 파일럿 범위를 확정하고 정규화→D1→Flutter 종단간 검증 계획 수립.

[추론] 지금의 가장 큰 위험은 화면·Mock 테스트가 동작한다는 이유로 서버 안전 경계와 실기기 연동까지 완성됐다고 판단하는 것이다. 새 기능 확대 전에 위 경계를 고정하는 편이 유지보수 비용을 줄인다.
