# AI·알고리즘·데이터 분석

## AI 여부

[사실] 현재 추천은 **학습 모델이 아니라 규칙 기반 계산**이다. 소스·의존성·계약에서 LLM 호출, 프롬프트, 모델 파일, 학습·추론 서버, 벡터DB, confidence 계산을 찾지 못했다. FITRUS URL의 `fitrus-ml` 문자열은 공급사 내부 구현에 대한 이름일 뿐, 이 저장소가 해당 모델을 소유하거나 성능을 검증했다는 근거가 아니다.

[추론] 지금의 기능은 평균·정합성·안전 게이트와 고정 계수만으로 표현되므로 AI가 있어야 구현 가능한 문제가 아니다. `docs/open-source-and-evidence.md`의 혼합효과/베이지안 계층모형은 향후 계수 검증 계획이며 현재 추천 코드가 아니다.

## 실제 계산

1. 측정은 같은 참여자·기기의 품질 통과 기록을 대상으로 한다. Flutter는 ID 중복 제거 후 시간순 최신4건을 선택한다. 서버 조회는 최근20건 안에서 필수 유한양수·품질 통과값4건을 고른다.
2. 필수5항목의 산술평균을 소수2자리로 반올림한다. Dart의 선택7항목 평균은4건 모두 값이 있을 때만 계산한다. 웹은12항목 전부 필수양수로 취급한다. Worker 평균은5항목만 반환한다.
3. Flutter·웹은 `fatMassKg/weightKg*100`과 bodyFatPct 차이>1, `weightKg/(heightCm/100)^2`와 BMI 차이>0.6을 경고한다. Worker에 이 검사가 없다.
4. 통증·어지럼·사용보류가 true면 BLOCKED, 필수자료 오류면 REVIEW로 반환한다. Flutter safety 기본 false는 명시적 문진 완료를 뜻하지 않는다.
5. 기본 300초·20Hz·50%에서 계수를 곱한다. 나이≥70이면0.90, 여성0.95/남성1.0, 평균 체지방이 여성20~35% 또는 남성10~28% 밖이면0.90이다. 20~70% 범위로 제한하고 정수 반올림한다.
6. 평균 BMI<18.5이면 추천 숫자는 남기되 REVIEW라 허가가 불가능하다. 위험 증상 BLOCKED는 엔진 recommendation=null이다.

근거: `app/algorithm/vibration-algorithm.ts`, `mobile-app/lib/algorithm/vibration_algorithm.dart`, `backend-api/src/algorithm.ts`.

| 입력/출력 | 실제 역할 |
|---|---|
| 나이·성별·평균체지방 | 강도 계수 결정 |
| BMI | <18.5 검토 상태; Flutter/웹에서 키·체중 정합성 검사 |
| 체중·체지방량 | 데이터 필수 및 정합성 검사용 |
| 골격근량 | 필수·평균·표시. 강도 계수를 직접 변경하지 않음 |
| BMR·수분·단백질·무기질·ECW·둘레·내장지방 | 선택 표시와 평균, 추천식에 직접 미사용 |
| 혈압·심박·스트레스·체온 | 표시 전용. 고혈압/심박 수치 등을 안전 게이트로 사용하지 않음 |
| 시간·주파수 | 기본 규칙의 상수, 사용자 신체조건에 따라 자동 변경하지 않음 |
| 강도% | UI/프로토콜 예정값. 실측 가속도·진폭 변환 없음 |

## 예제의 의미

[사실] 공통 fixture JSON은 키154cm·평균BMI17.75 → REVIEW, 여성38%/남성45%다. 웹·Flutter 현재 데모는 키150cm·평균BMI18.7 → READY(안전 응답 조건 별도)로 구성한다. 같은38%라도 상태와 입력이 다르므로 “공통 fixture와 UI가 같다”고 쓰면 부정확하다.

[사실] 현재 node:test5개·Worker알고리즘4개·Flutter알고리즘5개는 fixture 값을 각 테스트에 따로 적었다. 공통 JSON 파일 자체를 읽어 세 엔진의 전 입력/상태/경고를 일괄 대조하지 않는다. 이번 격리 검사는 서버가 체지방25%·체지방량1kg·체중45kg의 모순에도 READY를 반환함을 확인했다. 따라서 기존 `algorithm-parity.md`는 선택된 예제의 일치 기록이다.

## 신뢰도·오류 대응

| 평가 항목 | 현재 사실 | 확인 필요/개선 |
|---|---|---|
| 모델·프롬프트 | 없음 | 향후 도입 여부 불명 |
| 데이터 전처리 |4건선택·평균·일부 정합성 | 측정일 유효기간, 시간대·식사·운동·수분 메타데이터 정책 |
| 출력 검증 | 상태·범위·버전·시간/Hz/강도 비교 일부 | 전체 DTO·룰 상호제약·최대시간·물리교정 검증 |
| 신뢰도 점수 | 없음 | 계수의 통계 불확실성·평가계획 |
| 환각 | 생성형 모델이 없으므로 해당 기능 없음 | 공급사 추정 오류는 별도 검증 필요 |
| 결과 실패 대체 | REVIEW/BLOCKED, 에러 표시 | FITRUS 장애에서 실데이터 대신 Mock 자동전환하지 않음. 안전한 중지 복구 필요 |
| 개인정보 전송 | Flutter는 코드/PIN·측정ID·문진, Worker proxy는 불투명 payload를 FITRUS로 보냄 | payload의 실제 개인정보·동의·보관·제3자 범위 미확정 |
| 비용·지연 | 로컬 계산 외에 Dio/Worker/D1/FITRUS 호출 | 측정 SLA·계약 가격·월 호출량·모델 비용 자료 없음 |
| 성능 지표 | 합성 fixture expected values와 UI 테스트 | 실제 참여자 데이터·임상 효과/안전성/예측오차 지표 없음 |
| 계수 선택 | 기존 문서는 PILOT 가설이라고 명시 | 전문가 승인·변경 사유·통계적 추정 근거 확인 필요 |

## 데이터 수명과 감사 추적

[사실] 공급사 raw→vitals의 source_raw_id 관계는 설계됐지만 실제 변환 코드는 없다. BIA raw_json은 외부 raw 테이블의 직접 FK를 갖지 않는다. authorize마다 측정세트·추천이 쌓이며 READY이면 별도 허가를 만든다. 허가에는 recommendation_id를 직접 저장하지 않고 결과JSON을 복사한다. 정상 실행 허가에 사용된 false 문진3개는 별도 감사 객체로 저장되지 않아, 사후에 ‘미응답’과 ‘명시적으로 증상 없음’을 구별할 수 없다.

[사실] 보관기간·삭제·정정·백업 복구·내보내기·비식별화 작업은 없다. 피드백은 upsert로 이전 값을 덮어쓰며 변경 이력과 updated_at이 없다.

[추론] 후속 데이터 연구 전에 세트·규칙·허가·세션·피드백을 연결하는 식별자와 문진 작성자/시간을 고정해야 재현 가능한 분석이 가능하다. 표준편차·범위가 계획 문서에 있더라도 현재 평균이 변동성을 대표한다고 해석하면 안 된다.
